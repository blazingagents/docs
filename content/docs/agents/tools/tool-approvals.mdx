# Tool approvals

Stay in control of what your agent does. For each tool you choose whether calls run freely, are blocked, wait for a person to approve them, or are reviewed by the model first. When a person has to decide, the agent pauses, your app shows the call, and the agent carries on once the decision is in.

## Approval policies [#approval-policies]

Each agent has two policies: `approvalInChat` for chat and stateless generation, and `approvalInTasks` for [tasks](/automation/tasks). Each policy has a `default` mode and a list of per-tool `overrides`. A matching override wins over the default.

| Mode | What happens to a call |
| --- | --- |
| `full` | Runs without approval. This is the default. |
| `deny` | Is blocked. |
| `manual` | Waits for a person to approve or deny it. |
| `auto` | The agent's model allows it, denies it, or asks a person. If the review fails, the call is blocked. |

This example lets chat tools run freely except `bash`, which needs a person, and lets tasks use only `read`. The agent needs the `workspace` tool group for these rules to be valid:

```typescript tab="TypeScript"
await client.agents.update({
  agentId,
  approvalInChat: {
    default: "full",
    overrides: [{ tool: { type: "builtin", name: "bash" }, decision: "manual" }],
  },
  approvalInTasks: {
    default: "deny",
    overrides: [{ tool: { type: "builtin", name: "read" }, decision: "full" }],
  },
});
```

```python tab="Python"
client.agents.update(
    agent_id,
    approval_in_chat={
        "default": "full",
        "overrides": [{"tool": {"type": "builtin", "name": "bash"}, "decision": "manual"}],
    },
    approval_in_tasks={
        "default": "deny",
        "overrides": [{"tool": {"type": "builtin", "name": "read"}, "decision": "full"}],
    },
)
```

To target an MCP tool, use `{ type: "mcp", connectionId, name }` with the tool's original name and a connection attached to the agent (`connection_id` in Python). Each tool can appear once per policy, and it must be available to the agent, so update your rules when you remove a tool group or connection.

Sending a policy replaces it, and leaving one out keeps it as it is. Each session and task run saves its approval policy in [agent configuration](/agents/configuration-snapshots). Later policy edits apply to new work.

<span id="review-availability"></span>
Only interactive chat can wait for a person. In tasks and stateless generation, there is nobody to ask, so `manual` calls and `auto` calls that need a person are blocked, and the agent carries on with the work it is allowed to do. Automatic review uses the agent's model, so it counts toward the turn's usage.

## Human approval flow [#human-approval-flow]

1. The agent proposes calls that need a person, and the turn pauses.
2. Your app shows the reviewer the tools and their arguments.
3. Your backend sends every decision of the round in one `continueChat()` call (`continue_chat()` in Python). An approval round is all the calls that are waiting at once.
4. The agent resumes in the same request. Approved calls run, and denied calls return a denied result to the agent. Your app streams the rest of the answer back.

The resumed run is called a **continuation**. It is a new turn in the same session, and it counts toward usage like any other. Nothing runs on its own: the work starts only when a client makes the call, and listing approvals never starts it.

If the chat uses [backend functions](/agents/tools/backend-functions), pass their handlers as `functions` on the same `continueChat()` call, whatever tool caused the pause.

## List and decide an approval round [#list-and-decide-an-approval]

On your backend, list the session's approvals and show the pending ones to someone allowed to decide:

```typescript tab="TypeScript"
const { data } = await client.sessions.toolApprovals({ agentId, sessionId });
const pending = data.filter((item) => item.decision === "pending");
for (const item of pending) {
  console.log(item.approvalId, item.toolName, item.input);
}
```

```python tab="Python"
approvals = client.sessions.tool_approvals(agent_id=agent_id, session_id=session_id)
for item in approvals.data:
    if item.decision == "pending":
        print(item.approval_id, item.tool_name, item.input)
```

When the reviewer decides, send one decision for every pending call and stream the resumed answer back. Check that the reviewer may access this session before you call this:

```typescript tab="TypeScript"
import { BlazingAgents, type ToolApprovalDecision } from "@blazingagents/sdk";

const client = new BlazingAgents({
  apiKey: process.env.BLAZING_AGENTS_API_KEY!,
});

export async function decide(
  agentId: string,
  sessionId: string,
  decisions: ToolApprovalDecision[],
): Promise<Response> {
  const continued = await client.continueChat({ agentId, sessionId, decisions });
  return continued.toResponse();
}
```

```python tab="Python"
from blazing_agents import AsyncBlazingAgents, ToolApprovalDecisionInput
from fastapi.responses import StreamingResponse

client = AsyncBlazingAgents()


async def decide(
    agent_id: str,
    session_id: str,
    decisions: list[ToolApprovalDecisionInput],
) -> StreamingResponse:
    stream = await client.continue_chat(
        agent_id=agent_id, session_id=session_id, decisions=decisions
    )
    return StreamingResponse(
        stream,
        headers={"x-vercel-ai-ui-message-stream": "v1"},
        media_type="text/event-stream",
    )
```

Each decision carries the `approvalId`, an `approved` flag, and an optional `reason`. A round that is missing a decision, repeats one, or mixes decisions from different rounds returns `validation_failed`. The response is the resumed answer as an AI SDK UI message stream, including any error at the end.

## Render the resumed answer [#render-the-resumed-answer]

Approvals use the AI SDK's [tool approval messages](https://ai-sdk.dev/docs/agents/tool-approvals) and UI message streams. Blazing Agents saves the decisions and resumes the agent, so send them through your backend route above rather than relying on `addToolApprovalResponse` alone.

In a custom UI, post the reviewer's decisions to that route. This prints the resumed answer as it streams in:

```typescript
const response = await fetch("/api/tool-approval", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ agentId, sessionId, decisions }),
});
if (response.body) {
  for await (const chunk of response.body.pipeThrough(new TextDecoderStream())) {
    console.log(chunk);
  }
}
```

With `useChat` and `addToolApprovalResponse`, the work happens in your backend instead. `BlazingAgentsChatTransport` posts the answered assistant message to your chat endpoint, where `createChatRelay` turns its approval responses into the `continueChat()` call and relays the stream. `BlazingAgentsDirectChatTransport` makes the `continueChat()` call itself. See [build a chatbot](/getting-started/chatbot).

This is the smallest client that works. Add the pieces your UI needs next, by hand or by asking your coding agent:

- **Decide the whole round.** Collect a decision for every pending call before you post. The calls in one round wait together, so keep all of their buttons on screen until every one is answered.
- **Render the answer.** The body is an AI SDK UI message stream. Parse it with `parseJsonEventStream` and `uiMessageChunkSchema` from `ai`, forward the `value` of each successful result (throw its `error` otherwise), then pass the chunks to `readUIMessageStream` and replace the displayed message by its ID each time it updates. See [reading UI message streams](https://ai-sdk.dev/docs/ai-sdk-ui/reading-ui-message-streams), and [chat transports](https://ai-sdk.dev/docs/ai-sdk-ui/transport) to fit this into `useChat`.
- **Show errors.** A status that is not OK means the decisions were not accepted. A failure in the resumed turn arrives as an `error` chunk at the end of the stream; pass `terminateOnError: true` to `readUIMessageStream` to stop there and show it.

## Retries and busy sessions [#retries-and-busy-sessions]

- Sending the same decisions again is safe; the first recorded reason wins. Reversing a decision returns [`tool_approval_decision_conflict`](/api-reference/protocols/errors#tool_approval_decision_conflict).
- Retrying after the round already finished returns [`tool_approval_continuation_settled`](/api-reference/protocols/errors#tool_approval_continuation_settled). Read the history for the outcome instead of sending again.
- Retrying while a continuation for the round is already running returns `session_busy`.
- While approvals are pending or a continuation is running, new chat turns and regeneration return [`session_busy`](/api-reference/protocols/errors#session_busy).
- A turn that waits for a decision takes no steering, so [steer a running turn](/platform/sessions-and-turns#steer-a-running-turn) fails with `steer_not_available` while the pause lasts; keep those messages in your queue. Once a continuation is running, it accepts steering again.
- Closing or cancelling the continuation stream cancels the resumed turn, the same as a chat turn. Forward your request's abort signal. A dropped stream cannot be rejoined, so read the outcome from the [history](/platform/sessions-and-turns#read-the-history).
- The decisions and the continuation save their results into the assistant message that asked for approval. A history poll with `after` does not return that update, so reload the newest page without a cursor while a tool part is `approval-requested` or `approval-responded`.
- A failed continuation reports its error in the stream or in the history. Retrying it does not run the tool a second time.

## Security [#security]

- Sign in and authorize the reviewer on your backend, and keep your API key there.
- Show the reviewer the saved tool and arguments, and send the decision for that approval ID. The decision cannot change the call.
- Approving a call never gives the agent a tool it does not have. If the agent's configuration changes in a way that affects a pending call, the old approval no longer applies.

See [security and credentials](/platform/security-and-credentials).
