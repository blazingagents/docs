# Built-in tools

Give your agent ready-made abilities without writing any tool code. You switch on each tool by name in the agent's `tools` list. A new agent starts with none, so it can only do what you turn on.

## Turn on tools [#turn-on-tools]

The `tools` list you send replaces the agent's whole selection, so read the current list and add to it. This example gives the agent read-only access to its files:

```typescript tab="TypeScript"
const agent = await client.agents.get({ agentId });
const tools = new Set(agent.tools).add("read").add("grep").add("glob");
await client.agents.update({ agentId, tools: [...tools] });
```

```python tab="Python"
agent = client.agents.get(agent_id)
wanted = ["read", "grep", "glob"]
tools = [*agent.tools, *(tool for tool in wanted if tool not in agent.tools)]
client.agents.update(agent_id, tools=tools)
```

```rust tab="Rust"
use blazing_agents::agents::AgentTool;

let agent = client.agents().get(agent_id).await?;
let mut tools = agent.tools;
for tool in [AgentTool::Read, AgentTool::Grep, AgentTool::Glob] {
    if !tools.contains(&tool) {
        tools.push(tool);
    }
}
client.agents().update(agent_id).tools(tools).await?;
```

Any combination of tools is valid, and each name can appear once. New sessions and task runs use the update. Existing sessions keep the tool list they saved. [MCP tools](/agents/tools/mcp-tools) are added through connections, not through `tools`.

The tables below sort the tools into groups so they are easier to scan. A group is only a heading: you cannot turn on a group by name.

## Read tool tags [#read-tool-tags]

Each tool in the SDK's tool list carries tags that describe it. Its first tag is its group: `files`, `planning`, `memory`, or `web`. A file tool also has one access tag that says what it can do to the workspace:

- `file_read` tools (`read`, `grep`, `glob`) never change workspace files.
- `file_write` tools (`write`, `edit`) change files.
- `execute` (`bash`) runs any shell command, so it can change files and do more.

An agent whose file tools are all `file_read` is read-only: it can look through its workspace but not change it. Leave out `bash` for a read-only agent, because a command can do anything a `file_write` tool can. Tags never turn a tool on; you still list tool names in `tools`.

This example turns on every read-only file tool:

```typescript tab="TypeScript"
import { AGENT_TOOLS } from "@blazingagents/sdk";

const readOnly = AGENT_TOOLS.filter((tool) => tool.tags.includes("file_read")).map(
  (tool) => tool.name
);
await client.agents.update({ agentId, tools: readOnly });
```

```python tab="Python"
from blazing_agents import AGENT_TOOLS

read_only = [tool.name for tool in AGENT_TOOLS if "file_read" in tool.tags]
client.agents.update(agent_id, tools=read_only)
```

```rust tab="Rust"
use blazing_agents::agents::{AGENT_TOOLS, AgentToolTag};

let read_only = AGENT_TOOLS
    .iter()
    .filter(|tool| tool.tags.contains(&AgentToolTag::FileRead))
    .map(|tool| tool.name.clone());
client.agents().update(agent_id).tools(read_only).await?;
```

## File operations [#file-operations]

| Tool | Access tag | What it does |
| --- | --- | --- |
| `read` | `file_read` | Read a file. |
| `write` | `file_write` | Write a text file, creating folders as needed. |
| `edit` | `file_write` | Replace exact text in an existing file. |
| `grep` | `file_read` | Search file contents. |
| `glob` | `file_read` | List paths that match a pattern such as `src/**/*.ts`. |
| `bash` | `execute` | Run a shell command and return its exit code and output. |
| `publish_artifacts` | none | Publish one to ten files as [artifacts](/agents/artifacts). |

These tools run in the agent's [workspace](/agents/workspaces). The workspace starts only when the agent calls one of them, so an agent with no file tools never starts it.

The agent works under `/workspace`. Relative paths resolve there, `bash` starts there, and paths that would leave it are rejected. Commands get no provider keys or application environment variables, and they can reach only the hosts the workspace's [network policy](/agents/workspaces#control-network-access) allows.

Writing a file does not deliver it anywhere. The agent must call `publish_artifacts` to hand a file to your application, and it can do that only in a chat session or task run, not in stateless generation.

### Tools that come with skills [#tools-that-come-with-skills]

An agent with [skills](/agents/skills) also gets `activate_skill` and `read`, whether or not you selected them. Without `read` in `tools`, that `read` opens only skill files, not workspace files. To run a script from a skill, the agent also needs `write` and `bash`: it reads the script, writes a copy into the workspace, and runs the copy.

## Memory [#memory]

| Tool | What it does |
| --- | --- |
| `save_memory` | Save a note. |
| `get_memory` | Read one saved note. |
| `search_memories` | Search saved notes. |
| `update_memory` | Change a saved note. |
| `delete_memory` | Delete a saved note. |

These tools work on the agent's [memory](/agents/memory). You can also add saved notes to every turn without any tool through `memoryInjectionEnabled`.

## Web search [#web-search]

| Tool | What it does |
| --- | --- |
| `web_search` | Search the public web and return matching pages. |

The agent sends a `query` of 1 to 1,024 characters and an optional `limit`. It gets back up to 10 results, which is also the default. Each result has a `url`, a `title`, and usually a `description` snippet. The tool does not fetch full page contents. When the results are too large to return whole, the tool returns the ones that fit and adds `truncated: true`.

Each successful search uses usage credit. A failed search is free. Blazing Agents bills web search itself, so it uses credit even when your model runs on your own provider key.

Blazing Agents sends each query to Exa, a third-party search provider. The gateway that routes the query does not list Exa as a zero-data-retention provider, so assume Exa can keep the queries it receives. Keep secrets and personal data out of searches, or leave `web_search` off.

## Verify durable file operations [#verify-durable-file-operations]

Check that files survive between sessions: write a value in one session, then read it back in a new one. Check the saved tool result rather than the agent's reply, because the model can paraphrase.

Use an agent with `write` and `read` turned on and attached to a Plus workspace for this check, and wait more than 10 minutes between the two steps so the workspace stops in between. A Core workspace would pass the check only while it is still running.

First, ask the agent to write the file:

```typescript tab="TypeScript"
const sentinel = "BA_DURABLE_42";
const writeTurn = await client.chat({
  agentId,
  message: {
    id: crypto.randomUUID(),
    role: "user",
    parts: [
      {
        type: "text",
        text: `Use write to create durable.txt containing exactly ${sentinel}.`,
      },
    ],
  },
});
await writeTurn.toResponse().text();
```

```python tab="Python"
import uuid

sentinel = "BA_DURABLE_42"


def ask(text: str) -> str:
    message = {
        "id": str(uuid.uuid4()),
        "role": "user",
        "parts": [{"type": "text", "text": text}],
    }
    with client.chat(agent_id=agent_id, message=message) as stream:
        for _ in stream:
            pass
        return stream.session_id


ask(f"Use write to create durable.txt containing exactly {sentinel}.")
```

```rust tab="Rust"
use blazing_agents::messages::UserMessage;
use blazing_agents::Client;
use futures_util::TryStreamExt;

let sentinel = "BA_DURABLE_42";

async fn ask(
    client: &Client,
    agent_id: &str,
    text: &str,
) -> Result<String, Box<dyn std::error::Error + Send + Sync>> {
    let mut stream = client.chat(agent_id, UserMessage::text(text)).await?;
    let session_id = stream.session_id().to_string();
    while stream.try_next().await?.is_some() {}
    Ok(session_id)
}

ask(
    &client,
    agent_id,
    &format!("Use write to create durable.txt containing exactly {sentinel}."),
)
.await?;
```

Then read it from a new session and check the `read` result:

```typescript tab="TypeScript"
const readTurn = await client.chat({
  agentId,
  message: {
    id: crypto.randomUUID(),
    role: "user",
    parts: [{ type: "text", text: "Use read to read durable.txt." }],
  },
});
const sessionId = await readTurn.sessionId;
await readTurn.toResponse().text();

const { data } = await client.sessions.messages({ agentId, sessionId });
const output = data
  .flatMap((message) => message.parts)
  .find((part) => part.type === "tool-read" && part.state === "output-available")?.output;
if (
  typeof output !== "object" ||
  output === null ||
  !("content" in output) ||
  output.content !== sentinel
) {
  throw new Error("Persistence check failed");
}
```

```python tab="Python"
session_id = ask("Use read to read durable.txt.")

page = client.sessions.messages(agent_id=agent_id, session_id=session_id)
outputs = [
    part.model_dump().get("output")
    for message in page.data
    for part in message.parts
    if part.type == "tool-read"
]
if not any(isinstance(o, dict) and o.get("content") == sentinel for o in outputs):
    raise RuntimeError("Persistence check failed")
```

```rust tab="Rust"
use blazing_agents::messages::UserMessage;
use blazing_agents::Client;
use futures_util::TryStreamExt;

let sentinel = "BA_DURABLE_42";

async fn ask(
    client: &Client,
    agent_id: &str,
    text: &str,
) -> Result<String, Box<dyn std::error::Error + Send + Sync>> {
    let mut stream = client.chat(agent_id, UserMessage::text(text)).await?;
    let session_id = stream.session_id().to_string();
    while stream.try_next().await?.is_some() {}
    Ok(session_id)
}

let session_id = ask(&client, agent_id, "Use read to read durable.txt.").await?;

let page = client
    .sessions()
    .messages(agent_id, &session_id)
    .await?;
let found = page
    .data
    .iter()
    .flat_map(|message| &message.parts)
    .any(|part| {
        part.kind == "tool-read"
            && part.fields.get("state").and_then(|state| state.as_str())
                == Some("output-available")
            && part
                .fields
                .get("output")
                .and_then(|output| output.get("content"))
                .and_then(|content| content.as_str())
                == Some(sentinel)
    });
if !found {
    return Err("Persistence check failed".into());
}
```

Always read the whole stream, as these examples do. The turn finishes its tool work and saves the session only when the stream ends.

## Failures and shared files [#failures-and-shared-files]

File changes are not undone when a turn fails or is stopped. Writes and edits that finished stay in the workspace, even though a failed turn saves nothing to the session. Turns that share a workspace can also change the same files at once, so coordinate writes when that matters.

## Production checklist [#production-checklist]

- Turn on only the tools the agent needs. Selecting a tool gives the agent that ability; it does not check who the user is. For example, `read`, `grep`, and `glob` let the agent look at files without changing them.
- Keep secrets out of prompts, commands, files, and tool arguments, including web search queries.
- Treat files, commands, and summaries the agent produces as untrusted until your application checks them.
- Put a person in front of risky calls such as `bash` with [tool approvals](/agents/tools/tool-approvals).
- Expect limits on input and output size, file operations, and compute. See [limits and reliability](/platform/limits-and-reliability).
