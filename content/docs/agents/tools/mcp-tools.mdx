# MCP tools

Give your agent the tools from any remote MCP server, such as your own internal API or a third-party service. You create a connection once, with its URL and credentials, then attach it to every agent that should use it. Blazing Agents stores the credentials, refreshes OAuth tokens, and discovers the server's tools at the start of every turn.

## Connect and attach a server [#connect-and-attach-a-server]

This example connects a server that needs a bearer token, checks that it exposes a `lookup_customer` tool, and attaches it to an agent:

```typescript tab="TypeScript"
const connection = await client.mcpConnections.create({
  name: "Customer tools",
  url: "https://mcp.example.com/v1",
  authType: "bearer",
  bearerToken: process.env.CUSTOMER_MCP_TOKEN!,
});

const test = await client.mcpConnections.test({
  mcpConnectionId: connection.id,
});
if (!test.ok) throw new Error(`${test.error.code}: ${test.error.message}`);
if (!test.toolNames.includes("lookup_customer")) {
  throw new Error("Expected a lookup_customer tool");
}

const agent = await client.agents.get({ agentId });
await client.agents.update({
  agentId,
  mcpConnectionIds: [...new Set([...agent.mcpConnectionIds, connection.id])],
});
```

```python tab="Python"
import os

connection = client.mcp_connections.create(
    name="Customer tools",
    url="https://mcp.example.com/v1",
    auth_type="bearer",
    bearer_token=os.environ["CUSTOMER_MCP_TOKEN"],
)

test = client.mcp_connections.test(connection.id)
if test.error is not None:
    raise RuntimeError(f"{test.error.code}: {test.error.message}")
if "lookup_customer" not in (test.tool_names or []):
    raise RuntimeError("Expected a lookup_customer tool")

agent = client.agents.get(agent_id)
if connection.id not in agent.mcp_connection_ids:
    client.agents.update(
        agent_id,
        mcp_connection_ids=[*agent.mcp_connection_ids, connection.id],
    )
```

```rust tab="Rust"
use blazing_agents::mcp_connections::{McpConnectionTest, NewMcpConnection};

let connection = client
    .mcp_connections()
    .create(NewMcpConnection::Bearer {
        name: "Customer tools".to_string(),
        url: "https://mcp.example.com/v1".to_string(),
        bearer_token: std::env::var("CUSTOMER_MCP_TOKEN")?,
    })
    .await?;

let tool_names = match client.mcp_connections().test(&connection.id).await? {
    McpConnectionTest::Passed { tool_names, .. } => tool_names,
    McpConnectionTest::Failed { error } => {
        return Err(format!("{}: {}", error.code, error.message).into());
    }
    _ => Vec::new(),
};
if !tool_names.iter().any(|name| name == "lookup_customer") {
    return Err("Expected a lookup_customer tool".into());
}

let agent = client.agents().get(agent_id).await?;
if !agent.mcp_connection_ids.contains(&connection.id) {
    let mut ids = agent.mcp_connection_ids;
    ids.push(connection.id);
    client
        .agents()
        .update(agent_id)
        .mcp_connection_ids(ids)
        .await?;
}
```

```go tab="Go"
connection, err := client.MCPConnections.Create(ctx, ba.CreateMCPConnectionParams{
	Name: "Customer tools",
	URL:  "https://mcp.example.com/v1",
	Auth: ba.MCPAuthBearer{Token: ba.NewSecret(os.Getenv("CUSTOMER_MCP_TOKEN"))},
})
if err != nil {
	return err
}

test, err := client.MCPConnections.Test(ctx, connection.ID)
if err != nil {
	return err
}
if !test.OK {
	return fmt.Errorf("%s: %s", test.Error.Code, test.Error.Message)
}
if !slices.Contains(test.ToolNames, "lookup_customer") {
	return errors.New("expected a lookup_customer tool")
}

agent, err := client.Agents.Get(ctx, agentID)
if err != nil {
	return err
}
if !slices.Contains(agent.MCPConnectionIDs, connection.ID) {
	_, err = client.Agents.Update(ctx, agentID, ba.UpdateAgentParams{
		MCPConnectionIDs: append(agent.MCPConnectionIDs, connection.ID),
	})
}
return err
```

The list of connection IDs you send replaces the agent's whole list, so the example adds to the current one. From the next turn, the agent can call `lookup_customer`. When a chat turn succeeds, the call and its result are saved in the session, so check them there rather than in the agent's reply.

<span id="generated-tool-names"></span>
The model does not see the server's own tool name. Each MCP tool gets a generated name that starts with `mcp__` and contains the original, such as `mcp__0123456789abcdef__lookup_customer__a1B2c3D4`. That generated name is what appears in session tool parts and in an approval's `toolName`. To match a tool in your code, read an approval's `tool` field instead, which holds `{ type: "mcp", connectionId, name }` with the server's own name.

A connection has no on or off switch. Attaching it to an agent is what makes its tools available, and one connection can serve many agents.

## Choose how to sign in [#choose-how-to-sign-in]

The server URL must use HTTPS and cannot contain credentials, a query string, or a fragment.

| `authType` | Use it when | What you send |
| --- | --- | --- |
| `none` | The server needs no credentials. | Nothing extra. |
| `bearer` | The server takes a static token. | `bearerToken` |
| `oauth_authorization_code` | A person has to sign in and grant access. | Optionally `clientId` and `clientSecret` together, and `scope`; finish sign-in in the dashboard. |

For every type except `oauth_authorization_code`, Blazing Agents checks the server before it saves the connection. If the check fails, nothing is saved.

Credentials are write-only. Responses never include bearer tokens, client secrets, or OAuth tokens.

### Sign in with an authorization code [#sign-in-with-an-authorization-code]

A connection that uses `oauth_authorization_code` starts with status `needs_auth`. To finish it, a tenant administrator opens the MCP connections page in the [dashboard](https://www.blazingagents.com/app), clicks **Connect**, and signs in to the MCP server. If the server's authorization server asks for a redirect URL, register `https://api.blazingagents.com/v1/mcp/oauth/callback`.

Only the dashboard can start this sign-in; no API key can. To replace a connection's URL or credentials from code, call `reconnect()`.

## Check a connection [#check-a-connection]

Each connection has a `status`: `connected`, `needs_auth`, or `error`. Treat `needs_auth` as a sign to reconnect.

`test()` returns the server's identity, response time, and tool names, or an error with one of these codes:

| Code | What it means |
| --- | --- |
| `MCP_CONNECTION_AUTHENTICATION_FAILED` | The server refused the token or OAuth sign-in. Get valid credentials, then `reconnect()`. |
| `MCP_CONNECTION_INVALID` | The URL is not the full `https://` address of the server's MCP endpoint. |
| `MCP_CONNECTION_UNREACHABLE` | The server is down, the address is wrong, or the server does not accept connections from the internet. |
| `MCP_CONNECTION_DISCOVERY_FAILED` | The server answered, but listing its tools, or finding its OAuth sign-in, failed. |

Run it again after you change credentials or the server changes, because tools are discovered live on every turn.

## What happens during a turn [#what-happens-during-a-turn]

At the start of each turn, Blazing Agents connects to every attached server and lists its tools. Blazing Agents does not quietly run the turn with fewer tools, so a failing connection fails the turn before the model runs, and the error message names the connection:

- A connection with status `needs_auth` fails the turn with [`mcp_connection_needs_auth`](/api-reference/protocols/errors#mcp_connection_needs_auth) (`409`). `details.connections` lists each such connection. Retrying does not help until someone [signs in again](#sign-in-with-an-authorization-code) or you `reconnect()` it, and a task run that fails this way ends as `blocked`.
- A server that cannot be reached, or a tool list that fails, fails the turn with [`mcp_connection_discovery_failed`](/api-reference/protocols/errors#mcp_connection_discovery_failed) (`502`). A retry can succeed once the server responds.

MCP tools that require the MCP task protocol are not offered to the agent.

Requests to the server use HTTPS and have [time limits](/api-reference/protocols/service-limits#mcp-runtime-timeouts) and [size limits](/api-reference/protocols/service-limits#mcp-payloads). Tool results have a size limit too, and a result that echoes a stored credential is rejected.

A redirect is followed only when it stays on the same origin and keeps the request's method. Any other redirect fails the request. If your server moved, `reconnect()` the connection with its new URL.

Each attachment decides what end-user context the server receives. Turn on forwarding of the turn's `userId` or selected `metadata` keys with `agents.updateMcpAttachment()` (`update_mcp_attachment()` in Python and Rust, `UpdateMCPAttachment()` in Go). The server receives that context as information only. It does not grant access.

With forwarding on, every tool list and tool call request carries the context in its `_meta` field under the `com.blazingagents/request-context` key. Only the parts you turned on are present:

```json
{
  "_meta": {
    "com.blazingagents/request-context": {
      "userId": "app-user-42",
      "metadata": { "plan": "pro" }
    }
  }
}
```

The context has a [size limit](/api-reference/protocols/service-limits#mcp-payloads). A turn whose context is larger fails.

<span id="approval-rules-and-server-changes"></span>
An [approval rule](/agents/tools/tool-approvals) names an MCP tool by the server's tool name. If the server renames or removes that tool, every turn of the agent is refused with [`mcp_connection_discovery_failed`](/api-reference/protocols/errors#mcp_connection_discovery_failed) (`400`) before the model runs, until you remove or change the rule. `details.issues` names the rule, the connection, and the tool. The issue's `path` is the rule's position in the approval policy the turn ran under, such as `/approvalInChat/overrides/1/tool`. For a session, that is the policy in its saved [`agentConfig`](/agents/configuration-snapshots). A session keeps the rule it saved, so its turns are refused until the server lists the tool again or you detach the connection. Update approval rules before you deploy a server change that renames or removes a tool.

## Reconnect or delete [#reconnect-or-delete]

`reconnect()` replaces a connection's URL and credentials under the same ID. With a bearer token or no authentication, the new details are checked first, and the old ones stay in use if the check fails. With an authorization code, the old credentials are dropped right away and the connection returns to `needs_auth` until someone signs in again.

A session or task run saves the connection IDs it starts with. The attachment, the connection details, and the credentials stay current, so these changes reach existing work at its next turn:

- Reconnecting changes the URL and credentials existing sessions and task runs use.
- Detaching a connection takes its tools away from existing sessions and queued task runs. A saved [approval rule](/agents/tools/tool-approvals) for one of its tools is skipped while the connection is detached. Attach it again to give the tools back, with forwarding off until you turn it on again.
- A forwarding change applies to every session.

A connection you attach later reaches only new sessions and task runs. Detach a connection from every agent before deleting it.

## Production checklist [#production-checklist]

- Use credentials with the least access the tools need, and keep them out of names, URLs, metadata, tool arguments, and logs.
- Forward `userId` or metadata only when the server needs it.
- Plan for server errors, timeouts, and a turn that fails because a connection needs sign-in.
- MCP tools follow the same [tool approvals](/agents/tools/tool-approvals) as any other tool.
- Review [security and credentials](/platform/security-and-credentials).
