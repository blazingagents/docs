# Security and credentials

Blazing Agents exposes a backend-only `/v1` trust boundary. Use backend credentials to establish Tenant context, keep third-party credentials in their dedicated stores, and let the tenant's application authenticate and authorize its own end-users.

## Backend-only access [#backend-only-access]

A Blazing Agents API key grants Tenant-wide access and must stay in a trusted backend. Provider keys, MCP credentials, and internal service credentials must not enter browser or mobile clients either.

<Callout type="warn" title="Keep credentials on the backend">
  Never place a Blazing Agents API key or another service credential in a browser bundle, mobile binary, public-prefixed environment variable, URL, or client-visible error.
</Callout>

An API key identifies a Tenant; it does not identify an end-user. End-user Attribution is an optional data label, not authentication or authorization. The tenant's backend must establish the end-user identity and enforce application access before calling the platform.

## Authenticate a backend client [#authenticate-a-backend-client]

Load the API key from the backend environment and perform a harmless Tenant settings read:

```typescript
import { BlazingAgents } from "@blazing-agents/sdk";

const apiKey = process.env.BLAZING_AGENTS_API_KEY;
if (!apiKey) {
  throw new Error("BLAZING_AGENTS_API_KEY is required");
}

const client = new BlazingAgents({ apiKey });
const settings = await client.tenant.get();

console.log(settings.name);
```

A successful call returns the authenticated Tenant's settings. Configure `baseUrl` as a backend setting when calling a non-default API origin.

## Dashboard API-key management [#dashboard-api-key-management]

Create, list, and revoke Tenant API keys from the authenticated dashboard at
[`www.blazingagents.com/app/keys`](https://www.blazingagents.com/app/keys). The
dashboard sends your current Supabase Auth session to the shared `/v1` surface;
these credential-lifecycle calls require that dashboard JWT. A Tenant API key
cannot create, discover, rotate, or revoke any Tenant credential, including
itself. The backend SDK and the public REST operation catalogue intentionally do
not expose this lifecycle.

Give each key a descriptive name for one workload or environment, such as
`Production API` or `Blazing Agents CLI (laptop)`. Choose an expiration preset
when the workload has a known lifetime, or select **No expiration** when an
explicitly long-lived backend credential is required. Expiration remains
optional.

The complete `ba_…` value is shown exactly once after creation. Copy it
immediately into the workload's environment or a secret manager; never put it
in source control, browser/mobile code, URLs, logs, or client-visible errors.
Later dashboard listings show metadata and a short fragment only, and the
service stores only a SHA-256 digest, not the plaintext key.

Rotation is replacement-based: create a new dashboard key, deploy it to every
backend instance, verify the workload, then revoke the old key in the
dashboard. Revocation is immediate and hard; an expired key also stops
authenticating. If a key is lost, create a replacement rather than expecting
Blazing Agents to recover the one-time value.

## Provider credentials [#provider-credentials]

A Provider create request accepts one API key, stores it in Supabase Vault, and keeps only a Vault pointer and last-four display fragment in the product table. Responses never return the full key. Provider updates can change only the name; replace a Provider to change its credential, type, or base URL, then move Agents and delete the old Provider.

Turn resolution and model discovery decrypt a referenced Provider key through a Tenant-scoped database operation. Discovery returns only normalized model IDs and makes no inference request. The key is not written to Session, Task, DBOS checkpoint, or Sandbox state.

A Vercel AI Gateway Provider accepts and stores only the Gateway API key. Underlying OpenAI, Anthropic, or other vendor keys, routing, fallback, Team policy, credits, and billing remain configured in Vercel and are neither accepted nor stored by Blazing Agents. Gateway catalog discovery is public and does not use or prove access by the saved key.

## MCP credentials and outbound access [#mcp-credentials-and-outbound-access]

MCP Connections support no authentication, bearer credentials, OAuth authorization code, and OAuth client credentials. Credential bundles are versioned in Vault; create, replacement, refresh, and deletion operations keep the product row and Vault state coordinated. Runtime resolution injects the active bearer or OAuth credential into the remote Streamable HTTP transport without exposing it as an Agent tool argument.

MCP setup and Tool failures return sanitized messages. Runtime checks reject discovered definitions or Tool results that contain protected credential values. Outbound MCP requests use a guarded fetch path that validates schemes and resolved addresses, bounds redirects, time, and response size, and removes sensitive headers on allowed cross-origin redirects.

## Sandbox and service boundaries [#sandbox-and-service-boundaries]

API and task-worker processes authenticate to the private Sandbox service with scoped, short-lived ES256 service JWTs. Every file or exec operation carries only its Tenant, Sandbox, and strict operation input. The trusted dispatcher resolves the current Tenant-owned Agent attachment before each Tool invocation.

Cloudflare Sandbox exposes Workspace files only under `/workspace`. The
Workspace policy selects unrestricted Internet access, an outbound host
allowlist, or offline execution.
Provider and service credentials remain in the API or task-worker dispatcher;
they never become files or environment variables inside the Sandbox.
Published Artifact bytes live in private R2 independently of their Workspace
source; the private Agent-avatar bucket is not mounted in the Workspace.

## Safe logging and operations [#safe-logging-and-operations]

- Load credentials from a backend credential store or server environment, and rotate them with an overlap period where the resource supports replacement-by-create.
- Never log `Authorization` headers, plaintext Provider keys, MCP credential bundles, OAuth credentials, full API keys, or presigned Artifact URLs.
- Log stable request and resource identifiers only after checking that the corresponding error surface permits them.
- Return sanitized application errors to clients. Do not assume arbitrary application logs are automatically redacted; explicitly omit credentials and sensitive request bodies.
- Treat credential fragments as display aids, not authentication material.
